# test-gen

引数 `$ARGUMENTS` で渡された対象ファイルに対して、正常系と異常系のテストを作り、すべて通るまで直す。

既存テストと形式がずれると、レビューや保守のコストが増える。そのため、先に既存の流儀を調べてから書く。

## 手順

### 1. 対象を読む

- `$ARGUMENTS` が空、またはファイルが存在しない場合は、ここで止めてユーザーに確認する。
- 対象ファイルを読み、公開されている関数・引数・戻り値・終了コード・副作用(ファイル、DB、環境変数、外部コマンド)を洗い出す。

### 2. 既存テストの形式を調べる

- リポジトリ内のテストを探し、1〜2 ファイルを読む。`tests/`、`test/`、`*_test.*`、`*.bats` などが手がかり。
- 次の点を把握して、新しいテストに揃える。
  - フレームワーク(例: bats、pytest、jest)と実行コマンド
  - ファイル名と配置の規則(例: `tests/test_<名前>.bats`)
  - テスト名の付け方、setup/teardown、ヘルパー、モックの方法
- 既存テストがない場合は、プロジェクトの言語から標準的なフレームワークを選び、CLAUDE.md に書かれた方針があればそれに従う。選んだ理由をユーザーに一言で伝える。

### 3. テストケースを設計する

- **正常系**: 代表的な入力で期待どおりの出力・終了コードになること。
- **異常系**: 引数不足、存在しないファイル、不正な値、外部コマンドの失敗、空入力、境界値。対象が失敗時に非ゼロで終了する、またはエラーメッセージを出す、といった挙動を実際に確認する。
- 対象の実装を読んで分かる挙動だけをテストする。仕様を推測して書くと、通すために実装やテストを歪める原因になる。

### 4. テストを書く

- 手順 2 で調べた配置と命名で、テストファイルを作る(既存があれば追記)。
- 外部への副作用(ネットワーク、本番 DB、ホームディレクトリ)が出ないよう、一時ディレクトリやモックを使う。
- テスト名は、何を確認するかが読んで分かるものにする。

### 5. 通るまで直す

1. テストを実行する(単一ファイルで実行できるコマンドを使う)。
2. 失敗したら出力を読み、原因を切り分ける。
   - **テストの誤り**(期待値の書き間違い、セットアップ不足): テストを直す。
   - **対象の実装のバグ**: テストを通すためにアサーションを緩めない。バグであることを報告し、実装を直すかどうかはユーザーに確認する。
3. 直したら再実行する。3 回続けて直らない場合は、試したことと現状を報告して止まる。
4. すべて通ったら、リポジトリの静的解析(例: shellcheck、lint)があれば、新しいテストにも実行する。

### 6. 報告する

- 作成・変更したファイル
- 追加したテストの一覧(正常系・異常系に分けて)
- 最終的な実行結果(通った件数)
- 見つけた実装上の問題や、テストしなかった箇所とその理由
